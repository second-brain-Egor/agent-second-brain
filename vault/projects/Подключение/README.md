# Подключение

## Суть

Проектная заметка по сетевым подключениям, VPN, прокси и схемам доступа для Agent Second Brain, Барыги и связанных серверов.

Здесь фиксируются рабочие схемы подключения без хранения паролей, токенов, приватных ключей и других секретов.

## Барыга: доступ к Claude с российского сервера

Проверка от 2026-05-05 показала: Барыга подключается к моделям не через общий VPN всей машины, а через отдельный SSH SOCKS-туннель.

### Общая схема

Барыга находится на российском IP, но трафик Claude Code выводится через отдельный прокси-туннель:

1. На сервере Барыги работает `anthropic-tunnel.service`.
2. Этот сервис поднимает локальный SOCKS5-прокси на `127.0.0.1:1080`.
3. Локальный SOCKS5 уходит наружу через SSH-туннель на сервер `37.233.84.178`.
4. `proxychains4` настроен на использование локального SOCKS5-прокси.
5. Telegram-скрипт Барыги запускает Claude через `proxychains4`.
6. В результате трафик Claude идёт не напрямую с российского IP Барыги, а через внешний IP туннеля.

### IP-адреса

- Прямой внешний IP Барыги: `185.23.35.88`.
- Внешний IP при выходе через туннель: `37.233.84.178`.

### Важная деталь по способу доступа к модели

Барыга использует Claude Code через OAuth/подписку, а не через Anthropic API-ключ.

В запуске указан режим `claude -p`, без API-ключа. Поэтому эта схема относится именно к доступу Claude Code через подписочный/OAuth-контур, а не к прямой работе через Anthropic API.

### Что это значит практически

- Общий VPN на весь сервер для этой задачи не нужен.
- Достаточно отдельного SOCKS5-туннеля для процесса, который обращается к Claude.
- Остальной трафик сервера может идти обычным маршрутом.
- Такой подход снижает риск поломать системную сеть, потому что туннель используется точечно через `proxychains4`.

### Диагностические ориентиры

Если Claude на Барыге перестанет работать, сначала проверять:

1. Работает ли `anthropic-tunnel.service`.
2. Слушает ли локальный SOCKS5-прокси `127.0.0.1:1080`.
3. Жив ли SSH-туннель до `37.233.84.178`.
4. Не сломана ли конфигурация `proxychains4`.
5. Запускается ли Telegram-скрипт Барыги именно через `proxychains4`.
6. Не протухла ли OAuth-сессия Claude Code.

### Шаблон аналога для нового сервера

Аналог Барыги настраивается не как WireGuard, а как точечный SSH SOCKS5-туннель для процесса Claude Code.

Минимальный состав:

- `openssh-client`;
- `proxychains4`;
- systemd-сервис `anthropic-tunnel.service`;
- SSH-доступ с нового сервера на выходной сервер `clawd@37.233.84.178`;
- локальный SOCKS5 на `127.0.0.1:1080`;
- запуск Claude Code через `proxychains4`.

Проверенная форма сервиса:

```ini
[Unit]
Description=SSH SOCKS tunnel to proxy Anthropic API
After=network.target

[Service]
Type=simple
ExecStart=/usr/bin/ssh -D 1080 -N -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes -o StrictHostKeyChecking=no clawd@37.233.84.178
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

Проверенная хвостовая часть `/etc/proxychains4.conf`:

```conf
strict_chain
proxy_dns
quiet_mode

[ProxyList]
socks5 127.0.0.1 1080
```

Критичное условие: с нового сервера должен быть рабочий неинтерактивный SSH-вход на `clawd@37.233.84.178`. Без этого service будет создан, но туннель не поднимется.

### Чего здесь не хранить

- SSH-пароли.
- Приватные SSH-ключи.
- OAuth-токены.
- Сессионные файлы Claude.
- `.env` с секретами.

Секреты должны лежать отдельно в защищённом месте, а в этой заметке хранится только схема и диагностическая логика.

## Джулиан: настройка удалённого WireGuard-подключения

Проверка от 2026-05-05 показала: история с файлом конфигурации у Джулиана относится к WireGuard, а не к SSH SOCKS-туннелю.

### Где найдены следы

- Проект Джулиан: `/home/clawd/projects/julian`.
- Отдельная память Codex: `/home/clawd/.codex/memories/wireguard-94-session-2026-04-06.md`.
- Системные конфиги WireGuard: `/etc/wireguard/hiddifywg.conf` и `/etc/wireguard/wg0.conf`.
- Системные параметры форвардинга: `/etc/sysctl.d/99-wireguard-remote.conf` и `/etc/sysctl.d/wg.conf`.

Секреты, приватные ключи и preshared keys в заметку не переносятся.

### Текущая схема на этом сервере

На сервере активны два WireGuard-интерфейса:

1. `hiddifywg`
   - порт: `38077/udp`;
   - серверный адрес внутри туннеля: сеть `10.90.0.0/16`;
   - есть peers для `PC (Windows)`, `Phone`, `Tablet`, `Laptop`, `PC MANUAL 2026`, `PC MANUAL RESTORED 2026-04-05`;
   - наружный выход настроен через `SNAT --to-source 37.233.84.178`;
   - интерфейс поднимается через `wg-quick@hiddifywg.service`.

2. `wg0`
   - порт: `51820/udp`;
   - серверный адрес внутри туннеля: сеть `10.91.0.0/24`;
   - есть один peer с адресом `10.91.0.2/32`;
   - наружный выход настроен через `MASQUERADE`;
   - интерфейс поднимается через `wg-quick@wg0.service`.

Включён IPv4 forwarding:

- `net.ipv4.ip_forward=1`;
- дополнительно включён IPv6 forwarding в `/etc/sysctl.d/wg.conf`.

### Что именно Джулиан проверял по серверу 94

Отдельная сессия от 2026-04-06 была про сервер `94.247.128.194` и Windows-клиент WireGuard.

Подтверждённая схема:

- интерфейс на сервере 94: `wg-kz2`;
- порт: `38077/udp`;
- сеть туннеля: `10.92.0.0/24`;
- сервер внутри туннеля: `10.92.0.1/24`;
- Windows-клиент: `10.92.0.2/32`;
- на сервере был включён `net.ipv4.ip_forward=1`;
- NAT был настроен правилом `MASQUERADE` для сети `10.92.0.0/24` через внешний интерфейс `enp3s0`;
- FORWARD был разрешён, явные ACCEPT-правила для `wg-kz2` присутствовали;
- сервер видел свежие handshakes от Windows-клиента.

### Вывод той сессии

Серверная часть на `94.247.128.194` выглядела рабочей: интерфейс поднят, handshakes есть, forwarding и NAT настроены.

Проблема тогда сместилась на сторону Windows-клиента: маршрут, поведение WireGuard-профиля или содержимое клиентского `.conf`.

Факты по Windows на паузе:

- использовались профили `guard-94-clean.conf` и `guard-94-clean-split.conf`;
- туннель поднимался;
- маршрут устанавливался;
- прокси был выключен;
- публичный IP оставался `46.138.166.104`, а не `94.247.128.194`;
- при включении WireGuard ломался обычный интернет и SSH до сервера 94;
- после выключения WireGuard доступ восстанавливался.

### Важная диагностическая проверка

Следующая полезная проверка, зафиксированная в памяти Джулиана:

1. Включить WireGuard на Windows.
2. На сервере 94 смотреть `wg show wg-kz2`.
3. С Windows сделать запрос наружу, например `curl`.
4. Сравнить счётчики transfer у peer.

Если при запросе растёт только handshake или почти ничего не растёт, проблема ближе к Windows-маршрутам/профилю. Если трафик приходит на сервер, но наружу не выходит, тогда смотреть NAT, FORWARD и внешний интерфейс.

### Что было похоже на "галочки"

В найденных системных следах явных GUI-настроек или списка "галочек" нет.

По симптомам речь могла быть о настройках Windows WireGuard-профиля и маршрутизации, прежде всего:

- `AllowedIPs`;
- полный туннель против split tunnel;
- endpoint сервера;
- отключённый системный proxy;
- поведение маршрута по умолчанию при включении туннеля.

### Чем это отличается от VPN-истории

Это не VPN и не WireGuard.

Это обычная схема удалённой работы:

- SSH-доступ на сервер;
- перенос файлов через `scp`;
- продолжение работы в Claude Code/VS Code Remote SSH уже на сервере.

Если нужна аналогичная настройка для нового VPS, базовая схема ближе к этому раннему сценарию: создать пользователя, настроить SSH-доступ, перенести проект, открыть удалённую папку через VS Code Remote SSH или работать в терминале по SSH.
