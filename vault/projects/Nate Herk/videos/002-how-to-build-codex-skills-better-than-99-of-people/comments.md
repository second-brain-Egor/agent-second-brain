## @Forever1C3

The only thing I’d maybe add to this process is don’t assume that running the same skill with the same model will produce the same outcome every time, unless the workflow is genuinely deterministic and doesn’t rely on the LLM making creative or interpretive decisions. Early on, I usually run a skill multiple times just to get a behavioural baseline... that way I've got a better idea of what produces unacceptable outcomes, vs. what’s acceptable, and what is actually the desired outcome. I find 5 runs usually a good start. From there, I like using separate judge/evaluator agents to score outputs against a rubric that I create for each judge to challenge the assumptions being made, test any edge cases, and track behavioural drift over time so it can then report into that human in the loop system you mentioned. Particularly early on, when feedback can help to identify failures that the automated evaluator didn’t anticipate. Once you find those failures, they can become regression tests so future improvements have to prove they didn’t break something that already worked. This is particularly useful in non-deterministic workflows because otherwise i find that agents start treating any successful feedback as evidence that its right and then start gradually reinforce its own assumptions, which can eventually create whacky unintended outcomes.  Needless to say I find having separate agents whose job is to challenge and compare results against the desired behaviour with various golden sets and look for drift tends to create a much stronger feedback loop than simply allowing the original agent to decide whether it has improved itself. (for what it's worth to anyone)
