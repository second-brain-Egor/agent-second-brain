## @regularSenseAppeal

Matt is spot on when he say that provisioning information (context) to coding agents in a systematic and reproducible manner is critically important (and extremely hard to get right). I've spent so much time designing different systems to do this, but they all seem to fail some way or another. 1) Must be easy to add data. Matt uses an inbox for docs to digest. That is super convenient, but goes against seperation of concerns. You need complete trust in the system, to not place docs inside the projects they concern. 2) The file digestion is inherently a lossy process and some docs cannot be safely reduced as they could hold agent outputs that are 'key findings' or other destillations that should go in exactly as they are. 3). Finding the right balance between a minimal index/wiki (to avoid bloating the context window) and yet provide enough information in the wiki for an agent know where to go for deeper dives when needed. 4) Find out when and how an agent goes to the raw file for ultimate information when needed. In practice the digest becomes the ground truth which is risky. 5) How to avoid the coding agent anchoring heavily on random shit you dumped in the brain at some point. It must be very easy for the agent to assess the quality of a doc. This makes it risky to dump loose ideas and abandoned projects as your coding agent will often think that those constitute something to model after. And metadata is not even truly enforcable with an LLM, so you never know when it just ignores metadata warnings. Just mentioning other projects in the wiki will see your agent rummage around old crappy projects trying to find some random stuff to model after. I constantly had to turn off the wiki when needing the model to think unanchored (which I very often do).

My latest approach (to be implemented) is using nested brains. Small local brains are much easier to get right for a single project. No need to have 'names', 'colleagues', 'topics' and stuff like that in a single app repo. These small brains can become linked to parent brains which work the same but at a higher level. Wish me luck 🙂

## @fflo92

Depends on what you want to do😅 usual way would be to start using ai by chatting, learning what matters in a prompt (context is key id say). Then go on to start use agent harnesses (claude code, codex, openclaw or similar) for some agentic work. There you should learn how to conenct tools/mcp’s to your agent, to give it more capabilities than just chatting or using the pre shipped tools from theese agentic harnesses. Then you should learn what skills are (basically just the things you want to do regularly written down as a generic, reusable prompt) and how to use them. Maybe add the concept of agentic memory to it (but this depends on the harness - some people also build “AiOS“ or “second brains“ for that) and from there you have the most fundamentals to create and use ur agents for whatever you want to do, e.g. as you mentioned video editing, or software development, add a TTS tool to create some telephone voice agent, etc.
