Граф тоже исправлен: разные README.md больше не схлопываются, Forumhouse, trading-bot и другие проекты идут отдельными узлами со своими связями.

По рабочему сценарию поиск тоже проходит нормально: запросы по Forumhouse, структуре форума и маршруту через Барыгу возвращают данные из проектной заметки, а не пустоту. То есть две корневые ошибки устранены, и контур памяти сейчас работает корректно.

Остался один реальный операционный сбой: в logs/bot.log идёт TelegramConflictError. Это не проблема памяти или графа, а конфликт polling в Telegram — бот получает updates не в одном экземпляре. По логам сейчас уже есть активный процесс python -m d_brain, но параллельно есть ещё один источник getUpdates, из-за чего Telegram периодически режет соединение.

Итог: ошибки с RAG и графом устранены, поиск по проектным знаниям работает корректно. Неправильной сейчас остаётся только работа Telegram polling: нужно оставить один активный экземпляр бота и убрать второй источник getUpdates. Второй источник — это второй клиент, который тоже делает getUpdates у того же Telegram-бота.

Проще говоря, один и тот же токен сейчас слушают как минимум два процесса одновременно.

⚠️ Для polling это конфликтная схема: Telegram ждёт одного потребителя обновлений, а когда приходит второй, появляется TelegramConflictError.

Что это может быть на практике:
дубликат запущенного python -m d_brain,
второй systemd-сервис,
старый процесс в screen/tmux,
локальный тестовый запуск бота параллельно с серверным,
или другой экземпляр/скрипт с тем же bot token.

Сам Telegram не говорит имя этого процесса. По логу видно только факт: кроме основного бота, кто-то ещё ходит в getUpdates с тем же токеном.
