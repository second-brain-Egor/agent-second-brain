 Тема
 Как дать ИИ готовый пример и получить свою реализацию нужной функции программы.


 Краткое содержание
 Нейт показывает собственную программу записи экрана, созданную с оглядкой на Loom, и
 объясняет, как REA помогает исследовать устройство приложений. Он советует выбирать
 отдельную функцию, отделять найденные факты от догадок и проверять собственную версию в
 работе.


 Основной вывод
 По мнению Нейта, конкретный образец и последовательная проверка помогают ИИ сделать
 нужную вещь лучше, чем общая просьба создать похожую программу.


 Что здесь является инструментом
 GitHub — площадка, на которой разработчик разместил репозиторий morluto/rea, то есть файлы
 программы и инструкции. REA — сам инструмент исследования приложений; Claude Code в
 примерах Нейта пользуется его результатами и пишет новую реализацию. Наша папка Nate Herk
 хранит материалы ролика и этот разбор.

 В ролике показана схема: человек задаёт вопрос → Claude Code обращается к REA → REA
 исследует приложение → возвращает наблюдения → Claude Code создаёт свою версию. Это видно
 на схеме взаимодействия.

 Сверка с документацией 14 октября 2026. Описание разработчика подтверждает: REA
 соединяет агента со средствами анализа через MCP и дополняется инструкциями исследования.
 Для JavaScript/Electron предусмотрен статический разбор; глубокий разбор машинного кода
 использует Hopper, Ghidra или IDA. Это больше, чем один текстовый навык. Анализ выполняется
 локально, однако результаты получает агент, поэтому локальная обработка не означает, что
 облачная модель никогда не увидит извлечённые сведения. Документация прочитана; установка
 и запуск REA в нашей среде не выполнялись.


 Основные идеи и тезисы
 1. Образец делает задачу конкретнее. Нейт предлагает показывать несколько хороших
 отчётов, роликов или выбранную функцию приложения. Они помогают объяснить желаемый
 результат, который трудно полностью описать словами. Это не гарантирует правильного
 понимания всех требований.

 2. Исследовать одну функцию проще, чем копировать приложение целиком. Для записи
 экрана он выделяет окно камеры, перемещение и размер этого окна, выбор записываемого
 экрана и управление записью.

 3. Подбирать средства под устройство приложения. Исследование Electron, машинного кода,
 сайта или Android-приложения требует разных способов. На экране выбора средств эти пути
 разделены.

 4. Сначала читать обзор, затем углубляться. Автор говорит, что полный анализ Loom занял
 более гигабайта. Предлагаемая последовательность — обзор → один модуль → путь выполнения
 конкретной функции. Уже сохранённое исследование не следует запускать заново без причины.
 Экран 09:17.

 5. Не превращать предположение в факт. Результаты размечают как непосредственно
 найденные, выведенные косвенно или неизвестные. Для найденного нужна ссылка на
 доказательство; для предположения — явная граница уверенности. Экран 09:47.

 6. Неизвестное может стать собственным проектным решением. На экране внутренности
 нативного записывающего модуля остаются неизвестными. Для собственной версии указаны API
 Chromium и проверка через ffprobe; это решение автора, а не доказанное устройство оригинала.
 Экран 10:23.

 7. Исследование завершается испытанием реализации. Нейт требует запускать программу,
 сравнивать поведение и исправлять расхождения. Чтение кода само по себе не доказывает, что
 соответствующее поведение было выполнено.

 Ограничения и спорные места
 • Оценка качества субъективна. По словам Нейта, агент с REA завершал работу медленнее, но
 давал лучший результат. Не приведены одинаковые исходные задания, полные журналы, число
 повторов, измерения времени, затрат и ошибок. Универсальное превосходство не доказано.

 • Будущая экономия — предположение. Нейт допускает, что готовые результаты
 исследования позволят выполнить реализацию более дешёвой моделью. В ролике нет
 измеренного сравнения такого режима.

 • Скриншоты результата не заменяют полный рабочий цикл. В показанных приложениях не
 проверены все ошибки, длительная работа, совместимость и сопровождение. Нет
 воспроизводимого набора испытаний Herk Recorder.

 • Доступно не всё устройство продукта. Автор ограничивает исследование имеющимися
 файлами и доступным поведением. Из них нельзя автоматически восстановить закрытую
 серверную часть, исходные комментарии или все проектные решения.

 • Замечание об авторских правах передано как позиция автора. Нейт призывает писать
 собственный код, не переносить чужие материалы и не пытаться проникать на закрытые
 серверы. Юридическая допустимость конкретного исследования в этом разборе не
 устанавливалась.

 • Утверждение о неспособности ИИ к творчеству — мнение Нейта. Его примеры показывают
 пользу конкретного образца, но не доказывают общий предел возможностей моделей.

 Практическая ценность для Егора
 Вывод разбора: наиболее полезен переносимый порядок работы — выбрать одну функцию или
 один удачный документ, описать наблюдаемое поведение, сохранить основания, отделить
 неизвестное и проверить собственный результат по тем же примерам.

 Для нашего бота такой образец может уточнять требования к отчёту, оформлению документа или
 поведению кнопки. Это применение идеи из ролика, а не уже выполненная доработка. Для
 повторяемых документов достаточно примеров и правил; REA становится предметно полезен
 именно при необходимости исследовать устройство программы.
